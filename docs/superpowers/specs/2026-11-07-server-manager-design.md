# Server Manager — спецификация v1.1

Дата: 2026-11-07  
Статус: проект спецификации для утверждения (Superpowers / Brainstorming → Design)

## 1. Назначение

Локальная интерактивная CLI-утилита для администратора Debian, объединяющая управление виртуальными хостами Nginx, службами systemd, существующими приложениями Docker Compose, SSL (Certbot) и компактную диагностику сетевых портов. Команды выполняются на сервере с привилегиями администратора. Утилита не имеет web API и не прослушивает сеть.

## 2. Подтверждённые решения

1. Интерфейс: Python 3 CLI с текстовым интерактивным меню, без обязательных сторонних Python-зависимостей.
2. Nginx: **только** `/etc/nginx/sites-available` и `/etc/nginx/sites-enabled`; не управлять файлами `conf.d` и произвольными `include`.
3. Отключение сайта: оператор выбирает вручную, отключать ли только сайт, останавливать службу, отключать ли её автозапуск. Перед остановкой показывать связанные сайты.
4. systemd: поддержка существующих unit-файлов и создание новых `.service`.
5. Docker: управление только **существующими Docker Compose** проектами и сервисами. Не создавать compose-файлы и не редактировать их.
6. Для существующих Docker-контейнеров разрешено по подтверждению применять `docker update --restart=no`, сохраняя первоначальные политики для возможного восстановления. Изменение непостоянно при пересоздании контейнера.
7. Новый Docker-сайт: привязка к существующему Compose-сервису либо явное указание локального IP и порта проксирования; при отсутствии достоверной связи с Compose-сервисом классифицировать как «внешний/неопределённый backend», не предлагать автоматическую остановку.
8. Certbot: отдельная явная операция после создания сайта.
9. Диагностика портов: компактная таблица вместо полного вывода `ss`.
10. По отдельному подтверждению — выборочная очистка **только выбранного Docker Compose-проекта**: остановка, удаление его контейнеров и образов, которые больше никем не используются; bind mounts и все Docker volumes сохраняются. Никаких глобальных prune.

## 3. Границы v1.1

### Входит
- Просмотр доступных и включённых виртуальных хостов; домены, пути к конфигурации, доступные upstream, состояние прокси.
- Создание нового сайта с HTTP reverse proxy на указанный адрес:порт.
- Включение/отключение сайта с корректным управлением симлинками.
- Поиск вероятного владельца localhost-порта: systemd unit или контейнер Docker Compose, плюс уровень уверенности.
- Просмотр/старт/стоп systemd unit, создание управляемого `server-manager-<name>.service`, enable/disable по подтверждению.
- Просмотр проектов и сервисов Compose, старт/стоп отдельного сервиса с помощью `docker compose`.
- Изменение restart-политики существующего контейнера (explicit opt-in), сохранение прежнего значения и предупреждение о пересоздании.
- Отдельный вызов Certbot с проверкой домена и наличия Certbot; диагностика SSL-сертификатов.
- Просмотр занятых TCP/UDP-портов и их владельцев.
- Dry-run, журнал изменений, резервирование и откат файлов Nginx.
- Отдельная опциональная операция «Остановить и освободить место» для целого выбранного Compose-проекта, с анализом mounts, данных и общих образов.

### Не входит
- Удаление исходников, репозиториев, каталогов с данными и Docker volumes. Удаление контейнеров/образов допускается **только** при отдельной подтверждённой выборочной очистке Compose-проекта.
- Редактирование Docker Compose YAML или создание контейнеров через `docker run`.
- Управление произвольными конфигурациями `/etc/nginx/conf.d/`.
- Полноценный разбор сложного Nginx DSL и поддержка конфигураций с множественными контекстами/upstream как гарантированно управляемых.
- Гарантия отключения Docker Compose автозапуска после внешней оркестрации либо пересоздания контейнера.
- Глобальный `docker system prune`, `docker image prune -a`, `docker builder prune`, очистка чужих проектов или общих кэшей; выборочная очистка чужого build-cache в v1.1 не поддерживается.
- Выпуск сертификатов для непроверенного чужого домена без подтверждения.

## 4. Меню

```
1. Сайты Nginx: список и состояние
2. Добавить сайт
3. Отключить сайт
4. Включить сайт
5. systemd: управление службами
6. Docker Compose: проекты, сервисы, выборочная очистка
7. SSL / Certbot
8. Занятые порты
9. Проверка Nginx
10. История изменений / резервные копии
0. Выход
```

Параметры запуска: `server-manager` — меню; `server-manager ports [--tcp|--udp] [--listen] [--sort port]` — короткий неинтерактивный вывод; `server-manager sites list`; `server-manager --dry-run` — предварительная проверка/план без мутаций. Уточнить окончательный CLI при реализации.

## 5. Nginx — модель и операции

- Каталог разрешённых конфигураций: `/etc/nginx/sites-available/`.
- Активность: запись в `/etc/nginx/sites-enabled/`, которая ссылается на файл в `sites-available`, и успешная проверка `nginx -t`. Наличие ссылки само по себе не доказывает, что текущий процесс Nginx применил конфигурацию.
- Извлечение `server_name`, `listen`, `proxy_pass` для обзора — консервативный анализ. При переменных, `upstream`-блоках, вложенных include, множественных proxy_pass, нескольких `server` на файл либо неочевидном разрешении порта — пометка «неоднозначно» и отказ от автоматической остановки backend.
- Для сайта, файлы которого содержат несколько виртуальных хостов, отключается **весь конфигурационный файл**; показать затрагиваемые домены и потребовать дополнительного подтверждения.
- Существующие файлы никогда не переписываются без явного разрешения. Для создаваемых файлов использовать валидированные безопасные имена, атомарную запись и строгие пути.
- Перед операцией: проверить конфликты `server_name`/слушающих портов в управляемых файлах, сохранить изменяемые файлы/ссылки, выполнить изменение, `nginx -t`, затем `systemctl reload nginx`. При ошибке `nginx -t` или `reload` откатить файлы и повторно проверить/перезагрузить Nginx; если rollback не удался, вывести аварийное предупреждение и пути к резервной копии.
- Имеющийся SSL/vhost, управляемый Certbot, нельзя незаметно переписать; чтение/отключение ссылки допустимы. При повторном включении исходная конфигурация сохраняется без модификаций.

### Создание сайта

Ввод: домен(ы), IP и TCP порт backend (по умолчанию `127.0.0.1`), режим backend `systemd existing` / `systemd new` / `Docker Compose existing` / `custom local endpoint`. Для systemd new: unit name, workdir, пользователь, argv/ExecStart, environment-file (опционально), порт. Для Compose: проект, сервис, проверенный host port либо явный endpoint. Никакого автоматического изменения Docker port mapping.

Генерация одного HTTP reverse-proxy server block: `listen 80`, `server_name`, корректные `proxy_set_header Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`; настраиваемое проксирование WebSocket лишь при необходимости. Входные значения валидируются, исключаются директивы/injection. Проверяется наличие пути назначения и доступность порта (если endpoint уже должен работать).

### Отключение

1. Выбор файла из `sites-enabled`, просмотр всех доменов и endpoint.
2. Проверка связи endpoint ↔ systemd/Compose (неоднозначность явно обозначается).
3. Показывать иные сайты, использующие тот же backend endpoint, и предупреждать о неизбежной остановке общих потребителей.
4. Оператор выбирает: (а) только сайт; (б) сайт + stop сервиса; (в) сайт + stop + disable автозапуска.
5. Показывается план действий и запрашивается подтверждение.
6. Сначала отключается сайт и проверяется Nginx; только после успешного применения выполняются действия по backend, отдельно учитывая частичное выполнение.

## 6. systemd

- Existing: список `.service` (name, load, active, enabled, description), фильтрация; связь с портом через PID/cgroup и сокеты, если удалось доказать.
- New: создание `/etc/systemd/system/server-manager-<name>.service` (неймспейс предотвращает перезапись чужих units). Строгая проверка имени, рабочей директории, пользователя, команды. `User=` — непривилегированная учётная запись, `WorkingDirectory=`, `ExecStart=`, `Restart=on-failure`; `EnvironmentFile=` лишь при безопасном пути и правах. `daemon-reload`, `start`, `enable` — отдельные подтверждаемые шаги.
- Не применять `disable --now` без явного выбора. Не удалять unit в рамках выключения сайта. Если служба не найдена или связь не подтверждена, не останавливать автоматически.

## 7. Docker Compose

- Discovery: только контейнеры с Compose-метками `com.docker.compose.project`, `service`, рабочей директорией/источником конфигурации (когда доступны); выбирать проект и сервис. Если каталог/файл Compose не найден — показать диагностику, не запускать команду наугад.
- Выполнение: `docker compose -f <verified-file> -p <verified-project> stop <service>` / `up -d <service>` с безопасным argv, строго после подтверждения.
- Определение портов: `docker inspect`, опубликованные host bindings. Если backend доступен через внутреннюю Docker-сеть, но Nginx работает на хосте, требуется фактическая проверка доступности endpoint; нельзя предполагать, что внутренний порт контейнера доступен с хоста.
- Для отключения политики перезапуска: сначала получить список контейнеров конкретного сервиса и `HostConfig.RestartPolicy`, сохранить исходную политику каждого в журнале, затем `docker update --restart=no <container-id>` только для явно выбранных контейнеров. `docker update` выполняется после остановки; при ошибках выводить частичный статус. Восстановление — только по сохранённому ID при существовании контейнера; без гарантий после `up --force-recreate`.
- Показать предупреждения о `restart:` в Compose, сторонних systemd units, иных процессах-автозапускателях. Если утилита не может их проверить, явно указывать «автозапуск не гарантированно отключён».

### Выборочная очистка Compose-проекта (новое в v1.1)

**Область действия:** только *целый выбранный Compose-проект*, а не один сервис (для сервиса с общими контейнерами/образами требуется отдельная спецификация). Очистка всегда **необязательна** и запускается отдельным пунктом меню после подтверждения; обычное `stop` не удаляет ничего.

**Цель:** сохранить все пользовательские данные, файлы проекта, `compose.yaml`, `.env`, bind mounts и **все** Docker volumes; удалить только повторно получаемые контейнеры и образы, принадлежащие выбранному проекту и не используемые другими контейнерами или проектами. Сеть и кэш сборки не удаляются целенаправленно; освобождённый объём может оказаться нулевым.

**Предварительная проверка (обязательна):**
1. Достоверно установить Compose project, путь к файлам конфигурации, список сервисов и их контейнеров, включая остановленные. Если состав проекта неполон/неоднозначен — отказ в автоматической очистке.
2. Сохранить инвентаризацию контейнеров: ID, сервис, image digest/ID, политики restart, имена/источники/назначения всех mount, их типы, опубликованные порты, конфигурационные пути. Секреты не писать в журнал.
3. Выявить **анонимные volumes**: после удаления контейнера обычное `compose up` может создать новый анонимный volume и не подключить старый. Если такие volumes присутствуют — **заблокировать очистку**, пока данные не перенесены в именованный volume или bind mount за пределами Server Manager. Никакого `rm -v`.
4. Проверить изменяемый слой контейнера: удаление контейнера уничтожает данные вне mounts. Показать явно это ограничение и требовать отдельного подтверждения, что важные данные сохраняются во внешних mounts. Если есть известные критичные пути без mount или нет уверенности в сохранности данных — отказ от очистки.
5. До удаления контейнеров выяснить, разделяются ли их image ID другими контейнерами (включая остановленные) и проектами. Не удалять общий image, не применять `--force`; если образ нельзя достоверно связать исключительно с проектом, пропустить.
6. Проверить наличие локальных образов `build:`: до удаления убедиться, что доступны Dockerfile, build context и необходимые зависимости; для `image:` убедиться, что образ можно получить из доступного registry. Если восстанавливаемость не подтверждена — образ не удалять.
7. Показать список контейнеров и images-кандидатов, защищённые mounts, предупреждения и **оценку**, а не гарантированную величину освобождаемого пространства (общие слои уменьшают фактический эффект).

**Применение:** после явного подтверждения и проверки актуальности инвентаризации: `docker compose ... stop`, затем `docker compose ... rm -f` **без** `-v`, только для подтверждённых сервисов проекта; после этого проверка ссылок на каждый image ID и адресное `docker image rm <image-id>` **без** `-f` лишь для безопасных и эксклюзивных кандидатов. Не использовать `docker compose down --rmi`, `docker compose down -v`, `docker system prune`, `image prune -a` или `builder prune`: их область может быть шире выбранного набора. Данные в именованных и анонимных volumes не удалять в любом случае. При частичном сбое — записать пообъектный результат и дать безопасный план восстановления.

**Восстановление:** `docker compose ... up -d` создаёт новые контейнеры, а удалённые образы повторно скачиваются или собираются, если источники доступны. Сохранённые ранее runtime restart policies Docker не восстанавливаются автоматически после пересоздания; показывать предупреждение и предложить их восстановление по ранее сохранённым значениям после новой проверки. Фактическое восстановление зависит от наличия образов, Dockerfile/контекста, registry и сохранности данных.

**Принцип:** очистка ресурсов не означает безопасного удаления приложения. Сохранение Docker volumes не гарантирует сохранность данных, записанных в writable layer контейнера; если доказательств достаточной сохранности нет, функция делает только `stop` и объясняет причину отказа от очистки.

## 8. Certbot

- Независимое меню: выбрать существующий включённый сайт → проверить DNS/80 доступность (возможность внешней проверки ограничена), установлен ли certbot/nginx plugin → просмотреть план → `certbot --nginx -d <domains>` в интерактивном режиме.
- Перед вызовом создать резервную копию сайта. После вызова проверить `nginx -t` и показать сертификат/срок действия; `certbot renew --dry-run` только по отдельной команде.
- Не удалять сертификаты при выключении сайта; сертификаты могут использоваться другими виртуальными хостами.

## 9. Диагностика портов

Источник: `ss -H -lntup` (требуются соответствующие права для PID), дополнительно Docker inspect для связи порта с контейнером. Таблица `PROTO | LOCAL ADDRESS | PORT | PID | PROCESS | SYSTEMD/COMPOSE`; сортировка по номеру порта, фильтры TCP/UDP/порт/процесс. Для нескольких процессов/сокетов — не скрывать конфликты, группировать с деталями. Unix-сокеты и соединения ESTABLISHED по умолчанию не включать. Если владельца установить нельзя, показывать `?`, а не угадывать.

## 10. Надёжность, безопасность и аудит

- Требовать root либо запуск отдельных команд через sudo; без сетевого сервиса.
- Команды исполнять через `subprocess.run([...], shell=False)` с таймаутами; запрет интерпретации shell-строк и необработанных путей.
- Перед изменением сайта: dry-run, backup, показ последствий, подтверждение, тест Nginx, reload, rollback для Nginx.
- Логировать timestamp, operator uid, action, target, before/after, success/failure, ошибки и путь backup. Никогда не логировать секретные значения environment variables или private keys.
- Резервные копии с ограниченными правами под `/var/lib/server-manager/backups/`; журнал под `/var/log/server-manager/`; состояние операций под `/var/lib/server-manager/state.json` (атомарные записи и блокировка).
- Защититься от symlink traversal/path traversal, перезаписи чужих unit, гонок конфигурации, дублирующихся доменов и двусмысленного владельца порта.
- Нет общей транзакции для Nginx/systemd/Docker: сохранять результаты каждого шага; при частичном отказе показывать восстановительные действия, не утверждать полного успеха.

## 12. Приёмочные сценарии

1. Просмотр включённых и отключённых файлов Nginx, включая сайт с несколькими доменами.
2. Отключение сайта не удаляет файл из `sites-available`, сертификаты и данные приложения.
3. При общем backend оператор видит другие зависимые сайты до остановки службы.
4. Ошибка `nginx -t` приводит к восстановлению прежней ссылки/файла; `reload` проходит отдельную проверку.
5. Создание systemd unit не перезаписывает чужой файл; новый unit запускается под заданным пользователем.
6. Обычный Compose stop не удаляет containers/volumes, а restart policy изменяется лишь по явному выбору.
6а. Очистка требует отдельного подтверждения, не удаляет ни один volume или bind mount, блокируется при анонимных volumes/риске потери writable-layer данных.
6б. Очистка пропускает image ID, используемые чужими контейнерами, и не выполняет глобальные prune.
6в. После очистки проверяется возможность восстановления через Compose, а частичные неудачи отражаются в журнале.
7. При неоднозначной привязке порта к backend автодействия запрещены.
8. После пересоздания Compose-контейнера интерфейс предупреждает, что политика restart могла восстановиться.
9. Certbot не запускается автоматически при добавлении HTTP-сайта.
10. Вывод портов компактный, сортированный и честно указывает неизвестных владельцев.
11. Работают dry-run и журналирование частичных неудач.
12. Повторное отключение уже отключённого сайта и повторное включение обрабатываются без повреждения конфигурации.

## 13. Порядок разработки после утверждения

Superpowers `writing-plans` → задачи: runner/models → ports → nginx discovery/transactions → systemd → Compose → выборочная очистка Compose с защитными проверками → создание и отключение сайтов → Certbot → интеграционные проверки в изолированной тестовой среде → README/упаковка. Каждый этап разрабатывается через TDD с mock-командами; опасные команды не тестируются на рабочем сервере без отдельного разрешения.

## 14. Оставшиеся решения реализации (не требуют нового продуктового выбора)

- Собственный минимальный интерактивный CLI на стандартной библиотеке, без rich/curses.
- Для спорных конфигураций Nginx выбор «просмотр вручную/отказ от автоматической остановки», без попытки переписать сложный config.
- По умолчанию считать локальный loopback endpoint предпочтительным; публичную привязку backend не создавать автоматически.
- Не модифицировать существующие чужие systemd units при подключении сайта; только systemctl enable/disable/stop/start после подтверждения.
